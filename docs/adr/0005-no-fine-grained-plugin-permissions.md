# ADR-0005：不设置细粒度插件权限系统

## 状态

Accepted — 用户于 2026-09-01 明确确认。

## 背景

工作站定位为开源、开放的插件平台，用户预计主要从 GitHub 与公开 Registry 获取插件。此前已经确认：时间线不是插件禁区，认证只代表平台承诺，未认证插件点击下载时警告后仍可安装，不削减功能。

此前候选文档仍保留了文件、网络、GPU、外部进程、整壳皮肤和同进程滤镜的权限申请或分级设想。用户明确认为不需要建立此类宿主权限系统。

## 决定

宿主不实现类似浏览器、移动系统或 Premiere UXP 的细粒度插件权限申请、运行时授权和能力白名单。

具体规则：

1. 已安装插件可以调用全部公开 Host API，不按认证状态削减时间线、项目、文件、网络、GPU、外部进程或 UI 能力。
2. 插件 manifest 继续声明页面、主题、滤镜、命令、模型、后台服务、输入输出类型、平台和硬件要求。这些是贡献描述、装配信息和兼容信息，不是权限申请。
3. 第三方/未认证插件在下载或安装时显示一次统一警告与免责声明；用户继续后不再逐项申请权限。
4. 插件更新可以展示新增贡献、运行要求和变更说明，但不因“新增权限”自动停用插件或要求重新授权。
5. 整壳皮肤、原生同进程滤镜、外部可执行程序和任意用户级代码均允许作为插件形态，不设置认证专属通道。
6. 宿主不自动提权；若插件需要管理员权限，由操作系统与用户处理。这不是工作站权限模型。
7. UI 命名空间、页面容器、快捷键冲突检测、扩展排序和同一时刻只激活一个整壳皮肤属于组合/冲突规则，不属于安全授权。
8. 事务、对象版本、项目格式校验和 Undo/Redo 继续适用于所有通过公开接口进行的工程修改，其目的为兼容性和恢复，不是功能审查。
9. 插件可以绕过 API 直接运行用户级代码，但直接改写内部工程文件不获得格式兼容承诺；开源代码本身也允许用户自行修改宿主。
10. 平台只对自己认证的插件承担审核、兼容和质量承诺；未认证插件后果由用户判断，市场可依据既定规则标识或下架明显恶意内容。

## 后果

### 正面

- 插件作者不需要设计大量权限声明和授权分支，时间线、滤镜、Agent、模型和整壳皮肤保持充分自由。
- 认证与未认证插件使用同一功能面，符合开源和小规模作者生态的现实。
- manifest 回归到装配、发现和兼容用途，不再混淆“能力类型”与“是否允许”。

### 负面

- 插件能以当前用户权限读取、修改或删除文件、联网、启动程序，并可能导致数据丢失或主程序崩溃。
- 统一安装警告不能准确表达每个插件的实际行为，用户需要依赖源码、作者信誉和平台认证判断。
- 同进程原生插件可能直接破坏宿主稳定性，无法通过权限系统阻止。

### 中性

- 进程隔离仍可用于崩溃恢复、依赖冲突和资源管理，但不作为权限沙箱。
- 能力声明、平台兼容声明和 UI 冲突信息仍然必须存在。

## 考虑过的替代方案

### manifest 声明细粒度权限，宿主默认拒绝未授权调用

不采用。管理和实现成本较高，也与用户要求的开放插件方向不符。

### 认证插件全能力、未认证插件受限

不采用。认证只表达平台质量承诺，不形成两套功能等级。

### 普通主题与整壳皮肤分成权限等级

不采用。二者是不同贡献类型；整壳皮肤可以在安装警告后直接启用，冲突由激活规则处理。
