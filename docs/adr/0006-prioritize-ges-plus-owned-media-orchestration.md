# ADR-0006：优先验证 GES + 自研媒体编排层

## 状态

已接受为首选验证路线；最终生产媒体引擎仍待验证结果确认。

## 背景

AI 创作工作站不是只复刻传统非线性剪辑器。它需要在共享项目与时间数据之上连接剪辑页面、生成模型、字幕、TTS、音频处理、实时滤镜、离线 AI 任务和第三方 Agent，同时允许官方基础剪辑插件被替换。

MLT 已经具备成熟的传统 NLE 语义，但其主要优势是快速获得传统多轨剪辑能力。若把产品核心建立在 MLT 的对象和处理方式上，可能使后续 GPU surface、有状态 AI 滤镜、实时管线、设备输入和跨插件媒体协作受传统 NLE 模型限制。

GStreamer 提供可组合媒体管线、时钟、缓冲、格式/内存协商和跨平台插件系统；GES 在其上提供时间线、轨道、图层、片段、预览和渲染语义。它更接近本项目需要的现代媒体执行底座，但 GES 的对象模型仍不能成为项目真相，否则插件生态会被绑定到单一实现。

## 决定

将 **GStreamer + GES + 自研媒体编排层** 设为官方基础剪辑插件的首选验证路线。

边界如下：

1. **Core 时间线契约是唯一主数据。** 项目、资产、时间关系、插件产物、归档、连接、事务和 Undo/Redo 不保存为 GES 私有对象。
2. **自研媒体编排层把 Core 快照编译为媒体执行计划。** 它负责时间映射、能力选择、资源预算、缓存键、预览/导出意图、插件效果连接和失败回报。
3. **GES 是可替换的时间线执行适配器。** 首轮使用其 clip、track、layer、pipeline 等能力完成基本播放和渲染，但公共 API 不暴露 `GESTimeline`、`GstElement`、pad、caps 或 GLib 指针。
4. **GStreamer 是媒体数据平面。** 优先利用其 demux、decode、encode、clock、buffer、D3D12/Vulkan/GL 等插件；缺少所需能力时允许接入自研 C++/Rust 元素或绕过某段管线。
5. **关键次世代能力允许逐步自研替换。** GPU 合成、零拷贝 surface、缓存、特殊时间映射、有状态时序滤镜和最终渲染调度可在验证后由自研实现接管，不要求永久服从 GES 的全部语义。
6. **MLT 降为传统 NLE 行为与性能参考。** 当前不再作为同优先级首选实现，但保留研究资料和必要的对照测试，不把“古老”本身当作技术淘汰依据。

官方实现的重点是把 GES/GStreamer **包装成稳定的产品媒体服务**，而不是让页面或第三方插件直接拼 GStreamer 管线。包装层需要负责固定运行时版本、元素/编解码能力发现、管线计划、错误归一化、进度与取消、诊断日志、GPU 内存类型追踪、Worker 重启重建和跨平台 surface 适配。高级作者仍可提供自定义 GStreamer 元素或整个替代媒体 Worker，但通过公开媒体契约接入。

这项决定只确定研究和验证方向，不授权开始产品代码实现，也不表示 GES 已通过生产采用门槛。

## 分层草图

```text
项目 / 时间线 / 插件产物（Core 主数据）
                  │
       自研媒体编排与计划编译层
       ├─ 时间映射与事务快照
       ├─ 能力/插件选择
       ├─ 缓存与资源预算
       └─ 预览/导出执行计划
                  │
          GES 执行适配器
                  │
        GStreamer 媒体数据平面
       ├─ 解封装/解码/编码
       ├─ 时钟/缓冲/音画同步
       ├─ GPU 上传/合成/显示
       └─ 自研或第三方元素
```

## 结果

### 正面

- 保留 GStreamer/GES 的成熟媒体管线能力，避免从裸 FFmpeg 开始重造所有播放基础设施。
- Core 与插件只依赖本项目契约，未来可以替换 GES 或其中的关键路径。
- GStreamer 的插件和内存协商模型适合 D3D12、Vulkan、Metal 等多平台后端方向。
- 自研层可以围绕 AI 片段、有状态滤镜、插件信息连接和 Agent 调用建立更适合本项目的语义。

### 负面

- 同时维护 Core 模型、自研编排模型和 GES 执行模型，存在语义映射成本。
- GStreamer 的 caps、时钟、线程和动态管线调试复杂，Windows 分发也较重。
- 若自研边界划分不清，可能出现“既重造 GES 又被 GES 限制”的双重成本。
- 预览与最终导出走不同元素组合时，可能产生颜色、帧精度或效果结果不一致。

### 中性

- GES 不再被看作整个产品架构，只是官方基础剪辑插件内部的一种执行适配器。
- 第三方插件不需要使用 GStreamer；它只需实现公开的页面、信息、媒体效果或任务契约。

## 主要风险与验证门槛

1. **语义失配**：用嵌套、变速、重叠、转场、字幕和多声道场景验证 Core 计划能否无损映射到 GES；不能映射的部分必须显式报能力缺口，不能静默改变结果。
2. **隐式 CPU 回退**：记录每段管线的内存类型和元素选择，检测 D3D12/CUDA surface 被自动下载到系统内存的情况。
3. **逐帧与 seek**：验证 VFR、长 GOP、反向、快速拖动和代理切换下的帧准确性。
4. **预览/导出一致性**：同一执行计划分别跑实时和离线模式，比较帧、色彩、音频延迟和插件参数。
5. **可替换性**：至少用一个最小非 GES 执行适配器证明公共契约没有泄漏 GStreamer 类型；此验证只做架构样件，不扩展为第二套完整引擎。
6. **故障隔离**：管线、原生插件或驱动崩溃不得破坏 Core 项目事务；重启 Worker 后可以由快照重建执行状态。

上述验证通过后，再把状态升级为正式生产选型；若失败，只复审失败的执行层，不推翻 Core 时间线与插件边界。

## 考虑过的替代方案

### MLT 作为主要引擎

传统 NLE 功能成熟、接入成本较低，但当前产品方向更看重现代 GPU 管线、媒体组件组合和逐步替换关键路径，因此降为参考基线。

### 完全自研媒体引擎

自由度最高，但需要立即承担 seek、时钟、音画同步、格式协商、缓存和跨平台后端的全部复杂度。当前选择先利用 GStreamer/GES 缩小重造范围。

### libopenshot

适合较轻量验证，但现代 GPU surface、复杂时序插件和大型工程上限证据不足，暂不作为首选。
