## 1. 记录方式

每种模型类型确认后补齐：

| 字段 | 含义 |
|---|---|
| 模型类型 | 用户可理解的能力类别，不是某个具体模型名称 |
| 主要任务 | 它在创作流程里解决什么问题 |
| 输入 | 文本、图片、视频、音频、字幕、时间范围或其他对象 |
| 输出 | 生成或修改的产物类型 |
| 时间语义 | 输出是否天然带时间，是否写入时间线 |
| 页面入口 | 哪些内置页或插件页会使用它 |
| 插件贡献形态 | 模型连接器、滤镜、工具、生成器、后台任务等 |
| 首批边界 | 首先必须覆盖的调用模式和明确不包含的内容 |
| 状态 | 用户确认 / 待澄清 / 后续 |

### 2.1 视频生成的首批候选能力实现

这些名称只是用来验证基座能不能兼容不同模型，不进入 Core 的固定类型名：

| 候选 | 用它验证基座必须支持什么 |
|---|---|
| MiniMax H3 本地插件 | 本地执行后端；图片、视频、音频等多模态参考；生成同步音频；插件自带模型参数和运行状态 |
| Seedance 2.0 云端插件 | 云端异步任务；短片段生成、参考生成、编辑和续写；同一系列存在质量/速度/成本不同实现 |
| Seedance 2.5 云端插件 | 更长片段、更多参考素材、按时间段描述镜头与局部修改；能力上限与 2.0 不同，不能只靠版本号替换 |

由这三种实现共同反推出的基座要求：

1. 视频生成插件必须动态声明自己支持文本生成、首帧/首尾帧、参考生成、续写、局部修改和原生音频中的哪些能力。
2. 视频生成页按插件声明显示参数；模型独有参数由插件提供，Core 不内置 MiniMax 或 Seedance 字段。
3. 提示词可以对应时间段，并引用项目素材、时间轴选区、片段、首尾帧、音频和已有生成版本。
4. 用户可以按提示词段选择不同插件和模型；同一项目不绑定唯一视频模型。
5. 本地与云端任务都进入统一任务系统，支持排队、进度、取消、失败、重试和结果归档。
6. 结果可以只进入素材库、插入时间轴、替换选区或成为当前片段的新候选版本；默认行为后续由用户决定。
7. 生成视频自带音频时，基座必须能保留内嵌音频，也能按用户选择拆成与视频链接的音频轨。
8. 被替换的生成结果不立即删除，进入版本记录或归档并保留原时间范围。

第一轮资料记录保存在 `docs/research/2026-08-31-video-generation-models-h3-seedance.md`，但不作为产品计划主线；后续只继续研究会改变上述接口和交互的事实。

### 2.2 LLM 提示词能力与 Agent 的关系

- LLM 是可替换的文本能力实现；Agent 是调用能力、管理上下文和编排多个步骤的角色，两者不是同一层。
- 本地无审查 LLM 的首要价值是提示词表达自由，不要求它同时完成复杂推理和整条创作流程。
- 第三方 Agent 可以使用更强的本地或云端模型做规划，再调用本地无审查 LLM完成特定提示词步骤。
- 手动在 LLM 页面生成提示词、在视频生成页调用提示词工具，以及由 Agent/MCP 自动调用，应该复用同一个提示词能力与产物格式。
- 提示词每次生成和改写都保留候选版本；绑定某个时间段后才获得项目时间语义。

### 2.3 ASR：MOSS 与 Qwen 对基座的要求

#### 用真实模型验证能力差异

| 能力实现 | 对宿主暴露的主要能力 | 基座不能作出的假设 |
|---|---|---|
| MOSS-Transcribe-Diarize 0.9B | 一次产生段落文本、起止时间、`S01/S02...` 说话人标签；支持长音频、50+ 语言、热词和可选声音事件 | 这种“一次全给”的结果只是某些插件的能力，不能要求所有 ASR 都返回说话人 |
| Qwen3-ASR 0.6B / 1.7B | 自动语言识别、52 种语言/方言转录、离线与流式模式、上下文提示 | ASR 本体不等于带时间字幕，也不等于说话人分离 |
| Qwen3-ForcedAligner 0.6B | 把已有文本与音频对齐，产生词级或字级时间；可在人工纠正文本后单独重新对齐 | 强制对齐是独立能力和独立模型，不应藏成 Qwen 专属的 Core 字段 |

Qwen 本地路线实际需要：

- 在 0.6B 与 1.7B ASR 中选择一个能力实现。
- 需要时间戳时，再配置 Qwen3-ForcedAligner 0.6B；没有它时只得到语言与文本。
- 普通离线转录可以使用 Transformers 后端；流式、高并发或服务化路线使用 vLLM。
- Qwen 当前流式模式不返回时间戳，也不支持批处理；流式文字只能先作为“暂定结果”。
- vLLM 官方不原生支持 Windows，Windows 工作站需要通过 WSL/Linux 服务连接；Transformers 后端可以由 Windows 本地插件进程承载。
- MOSS 与 Qwen 当前依赖的 Transformers 版本不同，因此插件运行时必须隔离，不能要求所有 Python 模型共用宿主环境。

#### 基座必须注意的对象与接口

1. **ASR 结果不是字幕轨本身。** 先保存可追溯的转录文档，再由字幕分段/发布步骤生成字幕项。这样词级时间、说话人段和人工重新分段不会破坏原始结果。
2. **转写、对齐、说话人分离、字幕分段是四种可组合能力。** MOSS 可以在一个插件内同时实现前三项；Qwen 可以由 ASR + ForcedAligner 组合；其他插件也可替换其中任何一步。
3. **结果字段均为可选。** 转录段至少有文本；`start/end`、词/字时间、`speaker`、语言、置信度和声音事件按插件能力出现，缺失时不能伪造。
4. **时间必须有来源基准。** 插件返回相对输入音频的时间，宿主记录源素材、源入点、时间轴选区和速度变换，再映射到工程时间；不能只保存浮点秒后丢失来源。
5. **说话人标签只在一次转录内有效。** `S01` 不能自动当成全项目固定人物；用户之后可以将局部标签合并、重命名或映射到角色/配音对象。
6. **切块由能力实现控制。** Core 提供所选音频范围，但不能擅自用统一长度切块；MOSS 的说话人一致性和 Qwen 的对齐长度限制不同。插件必须回报切块、重叠和全局时间偏移。
7. **输入音频视图要明确。** 请求需要区分原素材音频、某个片段/轨道、选区混音或经过 BGM 分离后的派生音频，结果持续引用实际输入版本。
8. **人工纠正与重新对齐分开。** 修改文本产生新转录版本；可调用对齐器更新时间，而不是重新做整次识别。
9. **离线批处理与流式状态分开。** 批处理结果可以一次事务发布为字幕；流式结果具有 provisional/final 状态，最终确认后再形成稳定字幕版本。
10. **本地 ASR 进入同一 GPU 资源协调。** 插件报告模型驻留、显存需求和释放能力；开始后续本地视频生成前，同样适用右下角显存指示与释放提醒。

### 2.4 TTS：共同对象与三种验证样本

#### 三个样本用来验证什么

| 能力实现 | 已核实的差异 | 对基座的意义 |
|---|---|---|
| FireRedAudio | 9B 统一音频语言模型；支持零样本 TTS、指令式 TTS、声音设计以及语义/声学语音编辑；当前生成主要覆盖中英文，结果默认带随机性 | TTS 插件不一定只是“文本转 WAV”，还可能同时提供声音设计和已有语音编辑；任务需保存随机种子与真实使用能力 |
| IndexTTS 2.5 | 单参考音频克隆；音色与情绪可分离；情绪可来自参考音频、向量或文字；支持语言选择、发音标注和 `duration_factor` 语速控制 | 声音档案、情绪控制、发音控制和时长控制必须是可选能力；UI 按插件声明显示，不能固化为某一模型字段 |
| GPT-SoVITS | 零样本/少样本声音克隆和跨语言 TTS；也包含训练/微调与声音转换相关工具 | “直接使用参考声音”和“训练得到声音资产”是不同生命周期；训练产物由插件管理，但项目可引用稳定的声音档案 |

#### 基座候选契约

1. 建立模型无关的 `VoiceProfile`/声音档案概念：包含用户选择的参考音频、可选参考文本、语言和角色关联；插件自己的 embedding、checkpoint 或缓存不写进 Core 固定字段。
2. 一条字幕或剧本段可以生成多个配音候选；每个结果保存源文本版本、声音档案、能力实现、参数、随机种子、生成时间与实际音频时长。
3. 目标字幕范围与生成音频实际时长分开。插件可以声明支持精确时长、语速因子或仅自由生成；不匹配时由用户选择改文案、重生成、变速、移动后续片段或保留溢出，默认策略仍待确认。
4. 批量字幕配音按分段任务组执行，支持逐段试听、局部重生成、间隙/重叠检查和整批事务提交；失败不应抹掉已确认的旧版本。
5. 本地 TTS 运行时接入统一显存状态、模型驻留与释放接口；FireRedAudio 这类大型统一模型和较小的专用 TTS 可以拥有完全不同的资源声明。

官方资料：

- FireRedAudio：https://github.com/FireRedTeam/FireRedAudio
- IndexTTS：https://github.com/index-tts/index-tts
- GPT-SoVITS：https://github.com/RVC-Boss/GPT-SoVITS

### 2.5 区域 OCR：先保存观测，再形成字幕

区域 OCR 的目的已经确定为提取烧录在视频画面里的字幕。它不是普通截图 OCR，也不是从视频容器读取现成字幕流。

候选处理链：

```text
视频范围 + 字幕区域
  → 按时间采样画面
  → 文本检测/识别
  → 跨帧跟踪与去重
  → 重建出现/消失时间
  → 人工校对
  → 发布为字幕轨
```

基座需保存三层不同对象：区域定义/关键帧、带帧时间与几何位置的 OCR 观测、合并后的字幕候选。这样插件可以替换采样、OCR、跟踪或去重算法，也能回看某条错字究竟来自哪些画面。具体 OCR 模型暂不决定。

### 2.6 音乐生成：完整音频产物，不假定可拆 stems

MiniMax Music 3.0 已验证“创作概念 + 可选歌词 → 完整歌曲”的调用形态，并使用歌词段落标签与细粒度时间描述表达歌曲结构，官方说明可生成最长约五分钟的完整歌曲。

基座因此需要：

- 把音乐描述、歌词、段落结构和生成音频作为相互引用但可独立修改的产物。
- 支持完整歌曲或 BGM 的素材入库、候选版本、时间线放置、裁切、循环/延展和淡入淡出。
- 只有插件明确返回分轨时才创建 stems；生成模型宣传中的“清晰分离感”不等于 API 会输出独立人声/伴奏轨。
- 云端或本地生成都进入统一异步任务；长音乐生成不能绑定页面存活。

官方资料：

- MiniMax Music 3.0：https://www.minimax.io/blog/minimax-music-3-0-next-generation-open-weights-production-ready-versatile-music-model

### 2.7 时间视频处理：离线插帧、实时帧生成与超分必须分形态

#### 插帧

- RIFE 是典型双帧/任意时刻插值能力，可对已有视频离线生成 2×、4× 等结果。
- Magpie Experimental 是捕获画面后的实时效果链，当前包含 DLSSFG、XeSSFG 等；它无法取得游戏引擎原生运动矢量、深度、曝光或相机矩阵，所需信息来自颜色帧估计或 Zero-MV 路线。
- 因此插件能力声明需要区分 `offline-derived-media` 与 `realtime-presentation`，并把颜色帧、运动、深度等输入标成 required/optional/unsupported，而不是设置统一的“游戏插帧模型”开关。
- 插帧还必须明确 `preserve-duration` 与 `slow-motion` 两种时间策略；前者提高采样帧率，后者改变片段时长并触发音频/后续剪辑关系处理。

#### 实时超分与 DLSS5/DLSSNR 滤镜

对本机 `C:\Users\18392\Downloads\压缩包\DLSS5Tool` 的只读检查表明，现有工具按连续 RGBA 帧调用同分辨率 DLSSNR：会保持一个按分辨率创建的 D3D12/NGX 会话，顺序处理帧；首次帧或非连续跳转需要 reset，分辨率变化需要重建 feature。当前有效控制集中在风格、强度、局部色调、局部结构和输出混合，而不是空间放大。

这反推出实时 GPU 帧滤镜至少要有以下生命周期，而不是只提供一次性文件转换：

```text
create(format, size, device)
→ process(frame, timestamp, reset?)
→ resize/reconfigure(...)
→ flush/dispose
```

宿主负责时间线解码、音频保留、预览调度和最终编码；插件只负责帧处理。实时预览效果可以在用户选择后烘焙为派生媒体，但不能要求每个实时实现都支持烘焙。RTX Video SDK 当前公开的超分、伪影减少和 SDR→HDR 也适合验证这类帧流效果接口。

#### 正经视频超分/修复

- SeedVR2 3B/7B 是高质量时序视频修复路线；官方原型明确使用跨帧窗口与高显存/多 GPU 推理，输出可能重新生成细节，不能当作普通锐化滤镜。
- FlashVSR 是一步扩散的流式 VSR 路线，官方实现依赖分块/流式上下文和稀疏注意力，证明“长视频分块 + 跨块状态/重叠”必须进入视频处理契约。
- 两者都应产生与源片段保持时间关系的派生视频；原音频继续由宿主链接或重混。用户可比较、替换、回退，而不是覆盖源文件。

- RIFE：https://github.com/hzwer/ECCV2022-RIFE
- Magpie Experimental：https://github.com/SAOG0721/Magpie
- NVIDIA RTX Video SDK：https://developer.nvidia.com/rtx-video-sdk/getting-started
- SeedVR2：https://github.com/ByteDance-Seed/SeedVR

### 2.8 BGM 去除与音频降噪：输出必须与时间线对齐

#### 音源分离 / BGM 去除

- Core 请求的是“从哪个素材、轨道、选区或混音版本分离哪些声部”，插件决定模型、分块、重叠和实际 stem 集合。
- 结果是一个对齐的 stem bundle；对白/人声、音乐、鼓、贝斯、其他等名称由插件返回。宿主可以将其作为链接轨道插入时间线。
- “去除 BGM”是选择保留对白/人声、静音或降低音乐 stem 的编辑操作，不破坏原始混音。
- Demucs 能验证双 stem 与多 stem、分段降低显存和相对增益等问题，但目前仅是候选，不代表首批指定模型。

#### 音频降噪 / 语音增强

- 实时低延迟降噪与离线高质量增强使用同一大类产物，但插件必须声明是否实时安全、固有延迟、声道/采样率限制和适用内容。
- 输出继续引用源音频及实际选区，并回报延迟、裁切、重采样或长度变化，宿主据此保持同步。
- 降噪结果可作为 ASR 输入、声音克隆参考或最终混音版本；这些下游步骤应记录自己实际引用的是原音频还是某个增强版本。
- DeepFilterNet 与 ClearerVoice-Studio 目前只用于验证实时全频降噪、离线语音增强和多任务插件的差异，具体首批模型待用户后续选择。

官方资料：

- Demucs：https://github.com/facebookresearch/demucs
- DeepFilterNet：https://github.com/Rikorose/DeepFilterNet
- ClearerVoice-Studio：https://github.com/modelscope/ClearerVoice-Studio

## 3. 记录原则

- 模型类型与具体模型分开。例如一种能力类型可以由多个本地或在线插件实现。
- 模型类型与页面分开。同一种模型能力可以被页面、时间轴工具、滤镜或 Agent 使用。
- 只有天然具有时间或与时间轴操作相关的输入输出才记录时间数据。
- 首批支持表示宿主契约、任务状态、结果对象和插件接入需要覆盖，不表示 Core 内置具体模型。
- 用户列出具体模型名称时，同时记录它所属的模型类型，但不自动把该品牌固化进 Core API。
