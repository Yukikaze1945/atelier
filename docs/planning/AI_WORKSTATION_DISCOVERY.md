## 2. 已确认的产品愿景

来源：用户在关联对话中的明确表述，以及本次任务说明。

1. 产品首先应当把剪辑软件本身做好，而不是把所有 AI 功能硬塞进本体。
2. 调色暂不作为主攻方向，但应保留未来接入能力。
3. ASR、TTS、Agent 和不同模型应能在后期通过插件接入。
4. 产品希望为插件市场留下可能性。
5. 最初目标是先共同形成详细计划；2026-09-07 已获用户编程授权。重大未定产品选择仍不自动视为用户决定，开发期实现选择须明示。
6. 用户演进顺序为 A → B → C：第一阶段先服务用户本人，同时考虑一小群懂 AI 的视频创作者，成熟后再扩展到普通大众创作者。
7. 产品规划重点不是围绕单一固定成片场景裁剪功能，而是先建立自由、可组合、可扩展的创作基座。
8. 长期目标包含由 Skill 指导 Agent 将 ComfyUI 工作流迁移为工作站插件，支持“保留 ComfyUI 执行的兼容封装”和“脱离 ComfyUI 执行器的独立迁移”两种方式；迁移 Skill 先让用户选择，再按所选方式执行。两种方式均为正式目标，详见 DEC-ECOSYSTEM-028。

### 2.1 用户参考工作流 WORKFLOW-001

这条工作流用于检验基座的表达力和扩展能力，不等于 Core 功能清单：

1. 在 LLM 页面中由 Agent 编写剧本。
2. Agent 通过 Skill 把剧本片段转换成视频生成提示词。
3. 在类似剪辑软件的视频生成页面中，用时间段对应的文本区域承载提示词，逐段生成视频。
4. 在普通视频剪辑过程中，也能随时插入 AI 生成片段。
5. 对选定片段分段添加 DLSS 5 滤镜或处理。
6. 去除或分离原视频 BGM。
7. 对音频进行 ASR 转录，或对视频自带字幕的选定范围进行 OCR 转录。
8. 对字幕进行纠正和翻译。
9. 根据字幕生成 TTS，并替换或新增音频。
10. 合成 BGM 与其他音频轨道。
11. 对成片或选定范围执行视频超分。
12. 压制并导出最终视频。

### 2.2 从参考工作流提取出的基座需求候选

以下只是需求候选，尚未决定具体实现：

- 同一个工程能够容纳剧本、提示词、视频、音频、字幕和处理结果。
- 文本不只有“字幕”一种语义；剧本段、提示词、字幕、翻译和 TTS 文本之间需要可追踪关系。
- 所有能力都应能作用于工程、轨道、片段、时间范围或素材选择，而不是只能处理整个文件。
- 生成、转录、翻译、TTS、分离、超分和压制都是可能耗时、可取消、可失败、可重试的任务。
- 中间结果需要保存来源与版本，以支持重新生成、替换、比较和回退。
- 插件产生的修改需要进入统一工程事务，避免失败后留下半套状态。
- 页面可以针对不同任务组织体验，但底层对象不能被页面各自私有化。
- “能串起来”不仅指按钮能互相调用，还包括时间、范围、语言、媒体版本和任务结果能够无损传递。

### 2.3 候选交互模型 UI-PROPOSAL-001：项目页面条 + 页面装配图

状态：页面节点语义、首版 ComfyUI 式节点骨架、预览行为和替换入口已确认；剪辑页已确认改为官方基础插件；时间线边界已选择方案 C：Core 定义稳定契约，插件提供实际实现。

用户提出的视觉与交互方向：

- 用户当前倾向一切主要围绕时间轴组织，但还没有把这一点定为最终架构。
- 每个项目可以选择若干不同页面，并为本项目设置页面条的组成与顺序。
- 默认界面使用类似 DaVinci Resolve 页面导航的横向页面条，保持日常使用简单直接。
- 预装官方基础剪辑插件的初始工作区进一步参考 DaVinci Resolve Edit 页面的成熟结构：素材池、源/时间线监看、下方多轨时间线和右侧 Inspector；借鉴交互骨架而非逐像素照抄。
- 页面条展开后显示页面装配图；图中的每个节点就是一个页面，点击节点直接进入该页面。
- 首版页面节点借鉴 ComfyUI 的深色卡片、端口和折叠/展开骨架；展开后插件作者可以加入带版本和迁移规则的可选项。
- 节点左上角提供页面预览按钮：悬停临时展示页面样子，单击固定展示，再次单击关闭。
- 节点右键菜单提供“替换节点”，小型选择页固定分为“同类型节点”和“同插件包节点”两个标签页。
- 页面节点不代表执行步骤，节点连线也不自动传递或执行任务；它只是帮助用户组装与理解项目的页面导航。
- 自动化只预留空间，由 Agent、工作流或其他插件通过独立扩展能力实现，不能偷渡进页面导航语义。
- 页面插件只是插件的一类；滤镜、媒体处理器、工具、导入导出器和自动化能力也应有各自扩展位置。
- 新增的“插件信息连接图”是另一套图：它只负责让插件之间交换有类型的信息、上下文和结果，不触发插件执行，也不改变页面装配图只负责导航的既有语义。
- 因而当前明确区分三种图：页面装配图负责页面导航；插件信息连接图负责信息绑定；Agent 通过 MCP 负责自动调用和流程推进。三者可以互相引用，但不能共用同一种连线含义。

这个提案仍需验证的问题：

1. 页面装配图只允许线性排序，还是允许分组、分支和多个页面条预设。
2. 素材页和导出页是否也像剪辑页一样完整插件化；项目中心作为应用入口是否始终由宿主提供。
3. 页面插件缺失、被禁用、卸载或升级后，页面节点和页面私有状态如何占位、保留与恢复。
4. 页面之间共享哪些宿主上下文，避免每个页面各自复制一套素材、选择和播放状态。

#### 开箱即用页面候选

用户提出开箱版本应至少呈现：

- 项目页。
- 素材页。
- 剪辑页。
- 导出页。

“项目页”的语义已经确认：它是应用启动后的项目中心，参考 DaVinci Resolve 的项目管理骨架；默认视觉按 DEC-UI-029 参照用户提供截图的灰阶、控件和信息密度。进入具体项目后的默认页面条仍由素材、剪辑和导出组成。

这里的“开箱即用”改为由安装包预装官方基础插件实现，不再意味着剪辑页面写死在 Core。官方基础剪辑插件提供默认剪辑页和基础时间线体验；用户可以不在某项目启用它，也可以换成另一套符合契约的剪辑/时间线实现。禁用或替换页面插件不能顺带删除项目中的时间线、片段和处理结果。

剪辑页插件化之后仍有三种可能的系统边界，必须由用户选择：

| 方案 | Core 保留什么 | 官方基础剪辑插件负责什么 | 主要取舍 |
|---|---|---|---|
| A. 只插件化剪辑 UI | 完整时间线模型、编辑引擎、播放与渲染 | 页面、工具布局和交互 | 跨插件最稳定，但替换编辑引擎的自由度最低 |
| B. 整套时间线都是插件 | 通用项目、产物、任务和插件连接 | 时间线模型、引擎、页面、播放与渲染 | 自由度最高，但多个时间线插件之间很难直接交换项目和修改结果 |
| **C. Core 定义契约，插件提供实现（已选择）** | 版本化时间线交换对象、通用事务/引用/时间语义 | 时间线引擎、剪辑页面、播放与处理实现 | 兼顾替换自由和互操作，但契约设计与兼容测试成本最高 |

用户于 2026-09-01 确认选择 C。Core 保留可长期读取和迁移的时间线契约、公共引用、时间语义及事务规则；安装包内的官方基础剪辑插件提供默认引擎、页面、播放预览和编辑处理。其他插件可以实现同一契约或通过有类型端口使用时间线能力，不依赖官方插件名称。

如果某个项目选用的时间线实现缺失，宿主仍要保存并识别契约层时间线数据，显示实现缺失状态，并允许安装官方基础插件或其他兼容实现后恢复；不能把“插件缺失”解释成“时间线不存在”。实现专有功能可以保存命名空间扩展数据，但必须声明离开该实现后哪些内容只能保留、不能编辑或会降级。

#### 项目中心与新建项目

项目中心是应用级入口，不属于某个项目的页面装配图。

顶部一级标签已确认：

1. **本地项目**：显示本机项目。
2. **插件市场**：无需先打开项目即可浏览、安装和管理插件。
3. **工作流模板**：管理用户保存的工作流模板。

明确不设置当前没有实际能力的“网络”和“云端”空标签；以后若增加远程或同步能力，应通过真实功能或插件贡献入口，而不是预留不可用页面。

本地项目页候选结构：

```text
┌ 本地项目 ─ 插件市场 ─ 工作流模板 ───────────────────┐
│ 搜索  排序  筛选             缩略图/列表切换          │
├───────────────────────────────────────────────────────┤
│ 项目卡片或项目列表                                    │
│ 缩略图、名称、修改时间、位置、画面规格、关联模板/流程 │
├───────────────────────────────────────────────────────┤
│ 导入项目                         新建项目  打开         │
└───────────────────────────────────────────────────────┘
```

项目卡支持缩略图与列表两种视图。候选项目操作包括打开、只读打开、重命名、移动/重新定位、复制、导入导出、归档、恢复和删除；具体操作集需要后续确认，不直接照搬 DaVinci 的右键菜单。

点击“新建项目”后，创建界面至少包含：

- 项目名称。
- 项目保存位置。
- 项目模板：空白、内置模板、用户保存模板、插件提供模板。
- 工作流连接：不连接、选择已保存的页面/插件组合预设、现场组装并保存新的组合。
- 创建摘要：将启用的页面、页面顺序、插件、基础配置、轨道/素材结构和缺失依赖。

“工作流模板”的语义已经确认：它不是可执行 Agent/节点自动化，而是页面与插件的组合预设，保存项目要使用哪些页面、页面顺序、启用哪些插件以及允许模板携带的基础配置。它只负责装配项目工作区，不自动执行任务。

页面节点可以提供折叠的高级选项，用于配置该页面插件允许模板携带的基础设置。已确认的首个实例是素材页节点的“默认导入方式”：展开节点下方高级选项后选择链接原文件或复制进项目。应用模板时写入项目配置，之后允许项目本地修改；修改入口暂未决定。

项目模板与工作流模板仍是不同对象：项目模板负责项目位置之外的初始工程结构和设置，例如画面规格、默认时间线、轨道/素材箱结构和导出预设；工作流模板负责页面与插件组合。项目模板可以引用一个工作流模板，但两者可以独立保存和复用。

关键状态：

- 没有本地项目：显示新建、导入和从模板开始的空状态。
- 模板依赖插件缺失：创建前列出缺失项，可安装、保留占位或返回换模板。
- 工作流模板已更新：项目固定当前模板版本，不自动变化；发现新版本后提示用户查看页面、顺序、插件和配置差异，由用户决定升级或继续保留当前版本。
- 工作流模板升级冲突：升级前展示项目本地修改、缺失插件和不兼容项；用户可以取消升级、保留旧版、回退上一版本或脱离模板成为独立组合。
- 项目位置不可写或离线盘缺失：不创建半套项目，保留用户输入并允许重新选择位置。

#### 主题、皮肤与替代外壳候选

状态：用户已提出像 DeepSeek Harness 一样通过插件换皮肤；技术可行，开放等级尚待确认。

建议把视觉扩展拆成三个层级：

1. **主题 Theme**：颜色、字体、圆角、间距、阴影、轨道色和其他设计 token；可热切换，兼容性最好。
2. **皮肤 Skin**：在主题之上更换图标、组件视觉、导航外观、时间轴装饰和预览资源；仍使用宿主公开组件与命名插槽。
3. **替代外壳 Shell**：替换顶栏、页面条、侧栏和主要布局，允许形成完全不同的工作站外观；自由度最高，但需要单独声明兼容版本和冲突，不与普通 Theme 混为一类。

共同候选规则：

- 主题/皮肤由插件安装，并可在市场设立主题专区和预览。
- 普通主题同一时刻只激活一个；切换后立即预览并持久化用户选择。
- 项目数据、页面数据和时间轴不属于主题所有，换肤或卸载主题不能改变工程内容。
- 插件 manifest 声明它贡献 Theme、Skin 还是 Shell；安装前展示会覆盖的 UI 范围和发现的冲突。
- 宿主保留“以默认外观启动/恢复默认主题”入口，作为皮肤加载失败后的恢复路径；这不限制插件功能，只保证用户仍能切换回来。
- 是否允许多个局部 Skin 叠加、是否允许每项目独立主题、Shell 是否能替换全部系统页面仍待确认。

### 2.4 插件交互必须覆盖的候选契约

以下是从 WORKFLOW-001 与 UI-PROPOSAL-001 推导出的研究清单，不是已确定 API：

| 契约面 | 需要回答的问题 |
|---|---|
| Contribution | 插件可以贡献页面、受控面板、命令、滤镜、能力实现、导入导出器或渲染阶段中的哪些内容？ |
| Context | 插件如何获得当前工程、播放头、时间范围、选中片段、轨道和素材引用？ |
| Data | 剧本段、提示词、字幕、翻译、音频、视频和派生结果使用哪些稳定类型交换？ |
| Port | 插件怎样声明输入/输出端口、方向、类型、数量、时间语义、读写模式和 schema 版本？ |
| Link | 用户手动拉线和系统自动匹配怎样建立持久连接；连接是一次传值、持续同步、请求/响应还是任务结果返回？ |
| Adapter | 两个相近但不同的插件类型由谁转换；如何发现适配器、展示损失并避免暗中改写数据？ |
| Capability | 调用方按能力选择具体插件/模型实现，还是直接依赖某个插件？默认、备用和用户选择如何表达？ |
| Job | 长任务怎样报告进度、取消、暂停、恢复、重试和资源占用？ |
| Transaction | 插件怎样自由而完整地修改工程，同时让整批修改进入 Undo/Redo、失败回滚与事件通知？ |
| Event | 时间轴、素材或任务改变后，插件怎样收到通知而不形成事件风暴或循环调用？ |
| Permission | 文件、网络、GPU、模型、剪贴板、工程写入和外部进程能力怎样声明并在安装前告知用户；哪些只提示、哪些需要确认？ |
| Persistence | 插件私有状态、节点参数、版本迁移和插件缺失占位符怎样进入工程文件？ |
| UI lifecycle | 页面何时出现、激活、休眠、恢复；插件崩溃后界面如何降级？ |
| Resource | 本地模型插件怎样报告显存占用、预计需求、驻留状态和释放能力；宿主怎样在多个模型任务切换时提示资源冲突？ |
| Automation | MCP 暴露哪些工程、时间轴、素材、任务和插件能力；可执行工作流怎样复用同一组公共操作并保留事务与结果？ |

术语说明：“能力实现”曾暂称 Provider。例如“语音转字幕”是能力，Whisper 插件与云端 ASR 插件是不同能力实现。这个词不必出现在用户界面中。

#### 插件信息连接图

用户已确认：插件可以像 ComfyUI 节点一样拉出信息连接，也可以根据可匹配的信息自动连接；一个插件处理后产生的结果能够返回给另一个插件或时间线继续使用。这里的“自动连接”只表示自动找到兼容端口并建立信息绑定，不表示自动运行下游插件。

借鉴 ComfyUI 的是“显式输入/输出 + 类型匹配 + 自定义类型”，不是照搬其页面或执行器。候选设计分两层：

1. **宿主公共信封**：对象 ID、类型 ID、schema 版本、来源、项目引用、可选时间范围、当前版本、任务/事务 ID 和归档状态。
2. **插件自有载荷**：插件可以用命名空间定义专有数据，例如角色设定、Galgame 场景、某模型的控制条件或专有中间结果。

插件端口至少声明：输入/输出方向、类型、必需/可选、单值/列表/流、是否接收时间范围、请求还是结果、是否允许持续更新。连接方式包括：

- 用户从输出端口拖线到兼容输入端口。
- 用户选择“自动连接”，系统按类型兼容、当前项目上下文、时间范围和已有空闲端口给出或建立信息匹配。
- 类型不完全相同时，经用户可见的适配器节点转换；适配器本身也可以由插件提供。
- 处理结果沿输出端口返回，可以进入另一个页面、项目产物库、时间线选区、素材版本或归档，而不是只能导出文件。

需要防止的失败模式：插件之间直接依赖彼此内部类；同名自定义类型冲突；持续上下文更新形成循环；自动连接选错端口；插件缺失后连接和数据一起消失；schema 升级后旧连接静默失效。候选对策是命名空间类型、版本协商、连接占位、更新来源标识、循环检测、适配器和自动连接预览/撤销。

执行边界已经确认：普通信息连接只让接收插件获得数据和上下文，插件仍由用户操作或由 Agent/MCP 显式调用。例如把时间线连接给字幕页后，字幕页获得可用的当前时间线、素材、选区、播放头和字幕轨信息，但不会自动开始 OCR、ASR、翻译或写入字幕。所有跨步骤自动化由 Agent 通过 MCP 调用公开能力并管理任务顺序；信息连接图本身不是工作流执行器。

#### 未来 Galgame 引擎插件

用户计划后续制作 Galgame 引擎插件，当前先作为长期插件形态和基座验收场景，不进入近期实现。

该插件可能贡献自己的项目页面、剧情/分支编辑器、角色与立绘资产、对白与选择、变量状态、运行预览和游戏导出器；同时通过信息端口接收剧本、角色设定、图片、视频、字幕/对白、TTS 音频和 BGM，也能把场景录制、过场视频或处理后的素材返回时间线。

这个场景用于检验基座能否承载“非线性项目 + 可选时间线工具”：Galgame 项目不必把线性时间线当作唯一结构，但可以连接官方剪辑插件或其他时间线插件处理视频并取回结果。Galgame 对话时间、分支状态和游戏运行时对象不能被强行压成普通视频片段。

### 2.5 产物、时间语义与归档候选规则

状态：时间数据适用规则已确认；归档细节仍待设计。

- 只有天然具有时间或确实与时间轴发生关系的产物才保存时间数据，不为所有对象强行制造时间字段。
- 在时间轴选区生成的视频、字幕、在时间轴生成的音频等，应保存对应的时间基准、持续时间、轨道或关联范围。
- 剧本、通用提示词、普通页面配置等没有时间语义的对象，不要求时间数据。
- 媒体文件自身的时长/帧率与它在项目时间轴上的放置位置是两类信息，应当区分。
- 被替换、删除或暂时不用的产物进入可搜索归档，而不是立即物理删除。
- 归档需要保留来源插件、生成参数、父级素材、原时间范围、原轨道位置、版本关系和创建时间等可追溯信息。
- 用户可以从归档找回产物，并选择恢复到原位置、素材库或新的时间线位置。

### 2.6 完整插件市场

状态：开放方向、基础界面、推荐页、分类、更新、统计与排序均已进入完整项目范围；GitHub Stars 已确定代替站内点赞，目录收录和下载统计口径仍待决定。市场不再按“轻量 MVP”裁掉后续能力，实施先后只能作为交付顺序，不能被解释为永久删减范围。

#### 开放策略

- 认证插件与未认证插件都可以出现在同一个市场中，保持生态开放。
- 认证插件显示明确认证标识；认证代表平台审核与兼容承诺。
- 未认证插件可以浏览和下载，但点击下载时先显示醒目警告与免责声明。
- 市场是否推荐、是否认证、是否第一方必须是三种独立状态：推荐是运营位置，认证是平台审核结论，第一方是所有权来源，不能混成一个徽章。

#### 市场标签页

1. **推荐**：承载平台自有插件、编辑精选和按场景组织的推荐集合。
2. **插件市场 / 发现**：搜索、分类、筛选、排序、浏览和下载全部插件。
3. **已安装**：管理本机插件、版本、启停、更新、卸载和扩展贡献。

是否另设独立“更新”顶级标签页仍待确认；候选方案是在“已安装”标签内提供更新筛选、更新数量徽标、单个更新和全部更新。

#### 插件条目样式

- 左侧：作者提供的插件图标。
- 主信息：插件名称。
- 来源：可点击的 GitHub 仓库地址。
- 内容：简短插件介绍。
- 状态：认证/未认证标识。
- 右侧：胶囊形下载按钮；已安装后显示对应状态。
- 指标：成功安装量与 GitHub Stars；界面使用 GitHub 星形标识和 Stars 名称，不建设或暗示站内点赞。
- 时间：加入市场时间与最新稳定版本发布时间分开保存；市场“最近更新”排序采用最新稳定版本发布时间。

#### 下载交互

- 认证插件：点击下载后进入正常安装流程。
- 未认证插件：点击下载 → 展示未审核提示、GitHub 来源与免责声明 → 用户确认后继续安装。
- 警告不阻止用户继续，也不削减插件能力。

#### 分类与排序

- 分类必须适应页面、滤镜、工具、模型、Agent、Skill、媒体处理、导入导出等多种插件形态。
- 一个插件可以属于多个类别；“插件形态”和“解决的任务”建议拆成两个维度，避免把滤镜、字幕、视频生成等概念塞在同一棵单选分类树里。
- 已确认需要：按成功安装量、GitHub Stars 和时间排序。
- 时间排序区分“最新上架”和“最近更新”；“最近更新”采用最新稳定版本发布时间。
- 搜索、类别、兼容性、认证状态、插件形态和排序应该能够组合，而不是彼此排斥。

#### 推荐页

- 推荐页必须允许平台稳定展示自有插件。
- 同时保留编辑精选、场景集合、新插件、热门插件等候选货架；具体货架和顺序由后续运营规则确认。
- 第一方插件必须标注“平台官方/第一方”，而不是仅靠推荐位置暗示。
- 推荐位需要独立的后台配置、排序权重、上架时间窗和下架能力；不要求一开始依赖黑盒推荐算法。

#### 已安装标签页完整能力

- 查看插件名称、图标、版本、来源和认证状态。
- 启用/停用。
- 更新。
- 卸载。
- 查看插件为当前项目或全局贡献了哪些页面、滤镜和其他扩展。
- 查看可用更新、版本说明、兼容性变化和来源变化。
- 单个更新、批量更新、失败恢复与回滚。
- 查看插件依赖、冲突、加载状态和当前项目使用情况。

评论、评分、主题专区、云备份、跨设备同步、诊断中心和加载顺序编辑不是本轮已确认需求，但必须作为完整范围评估项保留，不能以“这是 MVP”直接排除。

### 2.7 本地 LLM 提示词能力与 Agent 自动化

状态：用户已确认产品定位；具体模型、页面布局和提示词对象字段仍待设计。

- 工作站允许通过插件接入本地或云端 LLM，用于编写和改写视频生成提示词。
- 本地无审查模型的核心价值是允许更激进、更自由的提示词表达，而不是替代完整 Agent。
- 本地模型通常较小，首批不要求它独立完成剧本规划、素材理解、任务调度和完整视频制作。
- LLM、Agent 与 Skill 分层：LLM 产生文本，Skill 提供针对模型或任务的提示词方法，Agent 负责选择并编排这些能力。
- 手动操作与自动化不冲突。用户可以在 LLM 页手动生成提示词；第三方 Agent 或可执行工作流也可以调用同一能力。
- 本地无审查 LLM 可以只是复杂自动化中的一个步骤；负责总体规划的 Agent 可以使用另一个更强模型。

### 2.8 GPU 显存可见性与释放提醒

状态：显存常驻指示和冲突提醒已由用户确认；自动释放策略尚未确认。

- 应用右下角长期显示显存指示，让用户在任意页面都能看到当前显存使用情况。
- 本地模型插件需要向宿主报告模型是否驻留、占用/预计需要多少显存，以及是否支持卸载或释放。
- 典型场景：本地 LLM 写完提示词后仍占用显存，用户紧接着启动本地视频生成。若预计显存不足，宿主应先提醒释放 LLM，避免直接提交后爆显存。
- 提醒至少应说明当前驻留模型、拟启动任务与资源冲突，并提供明确的“释放后继续”路径。
- 当前只确认“可见 + 提醒 + 可释放”，不擅自决定默认自动卸载、提醒阈值、是否保留模型缓存或多个 GPU 的调度方式。
- 显存协调服务于本地模型之间的资源交接，不限制插件访问 GPU 的自由度。

### 2.9 MCP 与可执行自动化工作流

状态：需要预留 MCP 接口和完全自动化空间已由用户确认；具体工具清单与工作流编辑器形态尚未决定。

- 工作站预留 MCP Server 接口，使第三方 Agent 能发现并调用工程、素材、时间轴、提示词、模型生成、任务和导出等公开能力。
- 第三方 Agent、插件页面、时间轴工具和未来的工作流编辑器应复用同一套宿主操作，不为自动化另开一套容易漂移的私有逻辑。
- MCP 调用产生的视频、音频、字幕、提示词和工程修改仍进入统一产物、任务、事务、版本与归档体系。
- 可执行自动化工作流可以组合这些能力，实现从剧本、提示词、生成、剪辑处理到导出的完整自动化。
- “页面与插件组合预设”仍只负责装配项目工作区；“可执行自动化工作流”负责调用工具和推进任务，两者必须作为不同对象保存，不能再次混为一谈。
- 自动化不绑定本地小 LLM。第三方 Agent 可以使用自己的模型与规划方式，并把本地无审查 LLM当作其中一个提示词工具。
- 后续仍需研究：首批 MCP 工具面、长任务订阅/取消、工程变化通知、工作流暂停恢复、失败重试和运行记录。

### 2.10 ASR 转录、对齐与字幕发布

状态：ASR 已确认为首批模型类型；用户当前主要使用 MOSS-Transcribe-Diarize 0.9B。以下接口形态来自 MOSS 与 Qwen3-ASR 的差异调研，尚未冻结字段定义。

- Core 不把 ASR 调用结果直接等同于字幕轨。ASR 先产生可校对、可版本化的转录文档，用户或工作流再把选定版本发布成字幕轨。
- 转写、强制对齐、说话人分离和字幕分段是不同能力；一个插件可以同时提供多个能力，也允许多个插件组合完成。
- MOSS 可一次产生段落时间与说话人；Qwen3-ASR 的时间戳需要独立 ForcedAligner，官方公开能力不包含说话人分离。宿主结果字段必须可选。
- 统一转录段候选字段包括文本、来源音频引用、相对起止时间、语言、说话人局部 ID、置信度、声音事件和词/字级对齐；不支持的字段保持缺失。
- 宿主负责把输入素材或时间轴选区转换为明确的音频视图，并保存其与原素材、派生音频、轨道和工程时间的关系。
- 长音频切块不能由 Core 统一写死；插件控制切块与重叠，并把全局时间偏移和合并结果返回宿主。
- 人工纠正文稿后，可以只运行强制对齐更新时码；旧文本与旧对齐保留为版本或进入归档。
- 流式 ASR 返回暂定文本，离线批处理返回最终文本；二者不能使用同一个“已完成字幕”状态。
- MOSS 与 Qwen 的本地 Python/推理依赖存在版本和操作系统差异，进一步确认了模型插件需要独立运行时或外部服务连接能力。
- 本地 ASR 也纳入 GPU 显存指示、释放提醒和任务资源协调。

### 2.11 TTS 配音、声音档案与时长冲突

状态：TTS 已确认为首批模型类型；FireRedAudio、IndexTTS 2.5 与 GPT-SoVITS 是首批接口验证样本，具体默认模型与页面交互尚未决定。

- 配音可以从剧本段、字幕、翻译文本或用户选中文本发起；生成结果引用确切文本版本、角色/声音档案和目标时间范围。
- Core 需要模型无关的声音档案，用来保存项目角色与用户选择的参考音频/文本关系；模型 embedding、checkpoint、训练缓存和专有字段仍由插件管理。
- FireRedAudio 证明插件可能同时提供零样本 TTS、指令式 TTS、声音设计与语音编辑；IndexTTS 2.5 证明情绪参考、情绪文字/向量、发音标注和语速控制可以独立出现；GPT-SoVITS 证明零样本使用与少样本训练是不同生命周期。
- 插件必须动态声明自己支持的语言、声音克隆、情绪、发音、速度/时长控制、语音编辑和训练能力；Core 不内置某个模型的参数面板。
- 字幕目标范围与生成音频实际时长是两个值。宿主必须检测短缺、溢出、段间重叠和空隙，但如何解决由用户或工作流选择，不擅自自动拉伸或移动剪辑。
- 分段批量配音支持逐段试听、局部重生成、候选比较和整批提交；已采用版本被替换后进入版本记录/归档。
- 本地 TTS 与其他本地模型共享显存可见性、释放提醒和运行时隔离，不要求所有音频模型共享 Python 环境。

### 2.12 区域 OCR 与音乐生成

状态：两种模型类型均已由用户确认；区域 OCR 的用途已明确，OCR 具体模型尚未选择；MiniMax Music 3.0 是音乐生成代表模型。

区域 OCR：

- 用途是复制已经烧录进视频画面的字幕，不等同于 ASR，也不等同于读取容器里的内嵌字幕流。
- 用户选择视频范围与画面字幕区域；插件可以负责帧采样、文字检测/识别、区域跟踪和跨帧去重中的一个或多个步骤。
- Core 分开保存区域关键帧、带来源帧/时间/几何/置信度的 OCR 观测，以及合并后的字幕候选；人工校对后才发布为字幕轨。
- 该结构允许以后更换 OCR 或重跑去重算法，而不用把整条字幕时间关系推倒重来。

音乐生成：

- MiniMax Music 3.0 官方公开形态是创作描述加可选歌词生成完整歌曲，可用歌词段落标签和细粒度描述表达结构，并支持最长约五分钟的长结构生成。
- Core 保存创作说明、歌词、段落结构、生成结果与候选版本之间的引用；音乐音频可以进入素材库或按目标范围放到 BGM/音乐轨。
- 循环、延展、裁切、淡入淡出和重新生成是时间线编辑行为；不把它们绑进具体模型 API。
- 只有插件实际返回分轨时才创建 stems；不能因为模型能够生成有人声的歌曲，就假设一定能单独输出伴奏和人声。

### 2.13 插帧、实时画面增强与视频超分的运行形态

状态：三种模型类型均已由用户确认；具体效果 API 尚未冻结。

必须分开的运行形态：

| 形态 | 代表实现 | 基座主要责任 |
|---|---|---|
| 离线插帧 | RIFE 系 | 提供片段/选区、帧时间与目标 FPS；区分保持时长和慢动作；保留音频/后续剪辑的时间关系 |
| 实时捕获帧生成 | Magpie Experimental 中的 DLSSFG/XeSSFG 路线 | 连续提交捕获颜色帧并管理显示节奏；不要求取得游戏引擎原生运动矢量、深度或相机数据 |
| 实时画面增强/游戏超分 | RTX Video VSR、Magpie 的 DLSS SR/RTX Video 路线 | 管理帧格式、输入输出尺寸、设备、实时状态与可用 GPU 余量 |
| 同分辨率神经后处理 | 本地 DLSS5Tool 的 DLSSNR 路线 | 保持有状态会话；跳转时 reset、分辨率变化时重建；暴露风格、强度、局部色调/结构等参数 |
| 高质量离线/流式视频修复 | SeedVR2 3B/7B、FlashVSR | 管理跨帧上下文、分块/重叠、长任务恢复、派生视频版本、显存资源与原音频链接 |

共同原则：

- 效果插件声明输入是颜色帧即可、可选辅助缓冲还是强制辅助缓冲；Core 不把运动矢量设成所有游戏插帧/超分的前置条件。
- 实时帧效果必须有创建、连续处理、重置/跳转、重配置/分辨率变化、刷新和释放生命周期；不能用一次性“文件转文件”接口替代。
- 实时预览与烘焙输出是不同能力。插件可只支持实时显示，也可支持宿主在离线渲染中复用；能力表必须如实声明。
- 离线视频处理产生派生媒体，不覆盖源文件；输出与输入帧时间保持映射，并继续引用原音频或新的混音版本。
- SeedVR2 与 FlashVSR 的官方实现都表明长视频需要模型自己控制窗口、分块、状态或重叠；Core 只提供媒体读取与目标范围，不能擅自逐帧拆成无上下文图片任务。

### 2.14 BGM 去除、音源分离与音频降噪

状态：音源分离/BGM 去除和音频降噪均已由用户确认；首批指定模型尚未决定，Demucs、DeepFilterNet 与 ClearerVoice 目前只作接口验证候选。

- 音源分离输入可以是原素材音频、视频音轨、某条轨道、时间轴选区混音或某个派生音频版本，任务必须记录实际输入。
- 输出不是单一“去 BGM 文件”，而是与输入对齐的 stem bundle；插件声明声部集合，宿主把选中 stems 作为链接音频片段/轨道放回时间线。
- “去除 BGM”默认是非破坏编辑：保留原混音和全部 stems，通过静音、降低或不使用音乐 stem 得到目标结果。
- 音频降噪分实时低延迟效果与离线高质量增强；插件声明固有延迟、采样率/声道限制、是否重采样、是否裁切和适用内容。
- 降噪输出可继续作为 ASR 输入、声音克隆参考或最终混音来源；每个下游任务都引用真实使用的音频版本，避免把结果错误归因于原素材。
- BGM 分离和降噪任务都必须保留工程时间映射，分块与重叠由插件控制，宿主负责版本、任务状态、取消、回退和时间线事务。

## 3. 尚未确认的候选原则

以下内容来自此前讨论或第一轮调研，只是待验证候选：

- Core 只负责统一编辑体验与工程一致性，AI 能力由插件提供。
- 插件按“能力”被发现，而不是互相依赖具体插件名称。
- 工程修改统一经过事务接口，以支持撤销、失败回滚和审计。
- 插件原则上可以获得广泛能力；认证标识、安装提示与免责声明负责表达风险，不以默认强隔离限制生态自由度。
- 插件声明命令、页面、面板、能力、平台与运行要求并按需激活；这些声明用于装配和兼容，不作为宿主权限申请。
- Agent 是插件能力的消费者与编排者之一，不拥有绕过工程规则的特殊通道。
- 插件市场是后期分发层，不应反向绑死早期 Core 设计。

## 4. 第一轮基线调研

### 4.1 时间轴交换：OpenTimelineIO

官方定义：OpenTimelineIO（OTIO）是剪辑信息的 API 与交换格式，支持片段、时间、轨道、转场、标记和元数据；它引用外部媒体，但不把音视频嵌入自身。

当前可推导价值：

- 可作为工程导入导出或跨软件交换的候选基础。
- 它不是完整播放、解码、特效或渲染引擎，不能仅凭 OTIO 构成剪辑 Core。
- 它的 schema 版本机制值得用于研究长期工程兼容性。

来源：

- https://opentimelineio.readthedocs.io/en/latest/index.html
- https://opentimelineio.readthedocs.io/en/v0.15/tutorials/versioning-schemas.html

### 4.2 多轨媒体框架：MLT

官方文档显示，MLT 面向多轨音视频组合，采用可插拔的 producer、consumer、filter、transition、link 服务，并以拉取帧和惰性求值组织处理。

当前可推导价值：

- 是“复用成熟剪辑/渲染框架”路线的候选对象。
- 需要专门验证：实时预览、现代 GPU 路径、字幕与复杂时间轴语义、Windows 分发、宿主扩展边界是否满足目标。
- 不能因为它具备多轨与插件就直接认定适合作为最终内核。

来源：

- https://www.mltframework.org/docs/framework/
- https://mltframework.github.io/mlt_web/docs/

### 4.3 媒体管线：GStreamer

官方架构以 element、pad、capability negotiation 和 plugin registry 组织媒体处理；插件只有在请求其元素时才需要加载。

当前可推导价值：

- 其“端口 + 能力协商 + 注册表 + 延迟加载”可作为媒体能力系统的设计参考。
- 它擅长媒体管线，不等于已经提供非线性编辑器所需的工程模型、时间轴交互、Undo/Redo 与用户体验。

来源：

- https://gstreamer.freedesktop.org/documentation/plugin-development/introduction/basics.html
- https://gstreamer.freedesktop.org/documentation/application-development/basics/pads.html

### 4.4 画面特效兼容：OpenFX

OpenFX 当前公开规范主要定义宿主与 2D Image Effect 插件之间的 C API，并通过宿主提供的 suites 建立能力边界。

当前可推导价值：

- 可研究为第三方视频特效的兼容层。
- 它不是 ASR、TTS、Agent、页面扩展或市场权限系统的通用插件协议。
- “支持 OFX”与“拥有自己的应用插件平台”应当被当作两个不同课题。

来源：

- https://openfx.readthedocs.io/en/latest/

### 4.5 应用级插件平台：VS Code

VS Code 官方扩展模型包含声明式 contribution points、activation events、稳定 API 与独立 Extension Host。官方明确用 Extension Host 降低失控扩展对启动、界面响应和 UI 内部结构的影响，并支持本地、Web 与远程宿主位置。

当前可推导价值：

- “声明贡献点 + 按需激活 + 受控 API + 独立运行宿主”值得作为应用插件层参考。
- 视频编辑涉及实时帧、GPU、共享内存和低延迟，不能直接照搬 Node/Web 扩展模型。
- 稳定 API 与实验 API 分层，可能适合解决插件生态早期仍快速演化的问题。

来源：

- https://code.visualstudio.com/api/advanced-topics/extension-host
- https://code.visualstudio.com/api/get-started/extension-anatomy
- https://code.visualstudio.com/api/advanced-topics/using-proposed-api

### 4.6 插件权限与 UI 边界对照研究

第一轮官方资料显示：

- VS Code 使用声明式 Contribution Points 注册命令、菜单、视图等扩展位置，并阻止扩展直接访问宿主 DOM，以降低扩展破坏 UI 稳定性和性能的风险。
- Adobe Premiere UXP 要求插件在 manifest 中声明本地文件、网络、剪贴板、外部进程、IPC 等权限；未声明权限默认拒绝。
- Chrome 在安装时显示敏感权限警告；插件更新新增警告型权限后会被停用，直到用户重新同意，并建议尽量使用可选的运行时权限。
- IntelliJ 使用带唯一命名空间的 Extension Points 注册不同类型扩展，可减少跨插件标识冲突。

后续用户决定：本项目不采用上述产品的细粒度权限申请和默认拒绝模型。保留的只是贡献类型、命名空间、兼容声明、冲突检测和统一安装警告；它们用于组合插件，不是授权。插件更新不因新增文件、网络、GPU、外部进程或 UI 能力而自动停用。详见 ADR-0005。

### 4.7 DeepSeek Harness 插件架构参考

已建立独立研究记录：`docs/research/2026-08-31-deepseek-harness-plugin-study.md`。

当前最重要的结论：

- DeepSeek Harness 以 Cordis 作为插件微内核；插件向共享 Context 注册服务、类型化事件和可撤销 effect，卸载时注册会一并撤销。
- 插件使用 `inject` 声明服务依赖，消费者通过稳定服务键查找能力，而不是直接导入具体实现。
- Profile 由有序 Bundle 与补丁层组合而成；这与“每个项目选择并排列页面/插件组合”存在可借鉴关系。
- 它把能力拆成 Service Definition、具体实现和 Consumer；这解释了此前的 Provider 术语，但本产品对外可以使用“能力实现”。
- UI 扩展通过宿主定义的 keyed slots 和 Host/Client 两半注册，不要求修改 Web 应用本身；这与受控页面、面板和设置插槽方向一致。
- 工具、Hook、UI、外部协议驱动、模型适配器、后台任务、MCP 和 Skill 使用不同插件形态，而不是把所有扩展伪装成同一种页面。
- 它的官方安全说明明确表示第三方插件、网络、进程、凭据和文件访问存在主机风险，沙箱与审批不能保证完全隔离；因此“无特权核心 + 第三方插件进程内运行”不适合直接照搬到视频工作站。

此前提出的“受保护宿主内核 + 受限第三方扩展”不符合用户期望，已不再作为默认方向。当前借鉴重点改为：可组合插件树、稳定服务契约、可撤销生命周期、项目级页面/插件组合、认证标识与安装提示。

时间轴不作为禁止插件修改的保护区。插件应能完整操作时间轴；Core 保留统一 API、事务、事件和工程格式不变量，是为了兼容性、Undo/Redo 与避免数据结构损坏，而不是限制插件功能范围。

## 5. 必须分开研究的六层问题

| 层 | 核心问题 | 不能混同为 |
|---|---|---|
| 工程与时间轴 | 片段、轨道、时间、嵌套、字幕、链接、撤销、版本迁移 | 媒体解码管线 |
| 项目数据连接 | 插件端口、类型、适配器、手动/自动连接、结果返回、schema 迁移 | 页面导航图或自动执行工作流 |
| 媒体执行 | 解码、缓存、代理、实时预览、音频、渲染与导出 | 工程交换格式 |

## 6. 规划路线（过程，不是技术路线）

1. 明确第一阶段用户与最重要的创作任务。
2. 明确产品边界：什么必须属于 Core，什么必须留在扩展层，什么明确暂不做。
3. 对编辑内核、媒体引擎、时间轴格式、插件数据连接、特效标准、插件运行时、Agent 协议分别调研候选方案。
4. 定义工程领域模型和关键不变量，再讨论技术栈。
5. 定义插件能力、权限、生命周期、进程边界、事务和兼容策略。
6. 定义 Agent / 模型接入方式以及它们修改工程的受控路径。
7. 明确非功能需求：延迟、分辨率、稳定性、硬件范围、离线/联网、恢复、隐私与分发成本。
8. 形成 2–3 套完整架构路线，使用同一组场景和指标比较。
9. 对高风险假设设计一次性验证原型；原型只在用户批准后实施。
10. 用户确认产品规格和 ADR 后，再编写里程碑与实施计划；仍不自动执行代码。

## 8. 决策登记

### DEC-PRODUCT-001：用户演进顺序

- 状态：用户已确认
- 决定：A → B → C。
- A：先为用户本人打造真正可长期使用的本地 AI 剪辑工作站。
- B：设计时考虑迁移到一小群懂 AI 的视频创作者。
- C：在产品和交互成熟后，再扩展到普通大众创作者。
- 当前影响：允许先从真实个人工作流验证价值，但不得把个人硬件、目录、模型或操作习惯固化为公共产品规则。
- 尚未决定：进入 B/C 的时间、指标、商业模式、平台范围与插件市场开放方式。
- 来源：用户于 2026-08-31 明确确认。

### DEC-PRODUCT-002：以自由基座为先

- 状态：用户已确认
- 决定：当前规划重点是制作可自由组合功能的基座，不用单一首要成片场景限制产品边界。
- 参考：WORKFLOW-001 用作覆盖度与组合能力的验收样例，而不是固定产品流程。
- 当前影响：后续先研究稳定对象、选择范围、任务编排、插件能力和结果追踪，再决定具体页面与内置功能。
- 尚未决定：基座以时间轴、素材关系图或二者组合中的哪一种作为主要权威模型。
- 来源：用户于 2026-08-31 明确纠正并描述实际流程。

### DEC-PRODUCT-003：页面节点只负责项目页面装配

- 状态：用户已确认
- 决定：页面装配图中的节点就是页面；点击节点进入页面，调整节点改变项目页面条的组成与顺序。
- 明确排除：页面节点和连线不表示自动执行流程。
- 自动化边界：为自动化保留独立接口，但具体自动化由插件实现。
- 补充边界：2026-09-01 新增的插件信息连接图是另一种对象，不改变本决定；页面节点仍只表示页面。
- 首版交互：节点采用 ComfyUI 式可展开骨架；插件可声明展开选项；左上预览按钮支持悬停临时预览、单击固定、再次单击关闭；右键替换页分为“同类型节点”和“同插件包节点”。
- 来源：用户于 2026-08-31 明确纠正。

### DEC-PRODUCT-004：插件类型开放，以装配规则处理 UI 冲突

- 状态：用户已确认；权限部分于 2026-09-01 修订
- 决定：插件不限于页面，也可以提供滤镜、主题、整壳皮肤、模型、外部进程等扩展。页面容器、命名空间、排序、快捷键冲突和整壳皮肤单活跃规则服务于装配一致性，不是权限限制。
- 权限策略：宿主不设置细粒度权限申请或认证/未认证功能等级；第三方插件统一安装警告后可使用全部公开能力。
- 尚未决定：首批扩展点清单与具体冲突优先级。
- 来源：用户于 2026-08-31 提出 UI 冲突问题，并于 2026-09-01 明确纠正为不设置插件权限；详见 ADR-0005。

### DEC-PRODUCT-005：时间数据按真实语义保存

- 状态：用户已确认
- 决定：产物天然具有时间或与时间轴操作相关时才保存时间数据；没有时间语义的对象不强行添加。
- 示例：时间轴生成视频、字幕、时间轴生成音频需要时间数据；无时间语义的对象不需要。
- 尚未决定：时间模型字段、跨帧率换算、嵌套时间线和归档恢复的精确规则。
- 来源：用户于 2026-08-31 明确确认。

### DEC-UI-026：页面节点采用 ComfyUI 式展开、预览与替换交互

### DEC-ECOSYSTEM-028：ComfyUI 工作流迁移支持两种可选方式

## 9. 当前活跃问题

插件信息连接的执行语义已经确认：只连接信息，不自动处理；自动化由 Agent/MCP 负责。默认技术架构已经确认，但必须先通过 Electron 原生 GPU 预览验证。媒体引擎首选验证路线已经调整为 GES + 自研媒体编排层，默认剪辑工作区参考 DaVinci Resolve Edit 页面。下一步不是平铺实现多个引擎，而是定义 Core 执行计划、GES 包装边界、可替换 GPU surface 和统一验证集；最终生产选型仍待测试。

闭源收费插件已确认在技术和 GStreamer 许可结构上可行，但主项目许可证（MPL-2.0、Apache-2.0 或 GPL + 插件例外）、付费入口和通用授权接口尚未选择，详见 `docs/planning/COMMERCIAL_CLOSED_SOURCE_PLUGIN_RESEARCH.md`。Serpent 的参考方式已确认改为功能/交互复刻并独立实现；官方素材页采用 DaVinci Media 页式的硬盘来源浏览器 + 项目素材库双区结构，导入方式采用工作流模板设置项目初始值、项目内可修改、单次拖拽可临时切换的方案。页面节点的 ComfyUI 式展开、预览与替换方向已经确认。素材页还将支持可替换 Embedding Provider 的语义素材搜索，并向 Agent/MCP 开放同一搜索契约；索引粒度、存储、重建和显存调度仍待研究。
