# dsh-market 第三方插件市场源码参考

> 日期：2026-08-31
>
> 源码基线：`dsh-market/dsh-market` commit `df2a16b1ed2dfaf1f2505e184e738c0d6d428945`（2026-08-30，release 1.38.1）

> 用途：分清 dsh-market 已实现的机制、其外部 Registry 提供的数据，以及 AI 创作工作站需要自行补齐的完整市场能力。

## 1. 身份确认

`dsh-market` 是 DeepSeek Harness 社区的第三方插件市场项目，不是 DeepSeek 官方核心功能。它作为插件安装进 DSH Web 的 Settings → Plugin Market。

项目仓库：

- https://github.com/dsh-market/dsh-market

参考截图：

![dsh-market 界面参考](https://raw.githubusercontent.com/dsh-market/dsh-market/da83292883be1b33e3c22a39580c5caee089ab45/assets/demo-en.png)

## 2. 它实际由哪几部分组成

`dsh-market` 不是一个把插件列表写死在前端的单页：

```text
awesome-dsh-plugin Registry
  └─ plugins.json：分类、名称、作者、GitHub、npm、Stars、下载量、加入日期
        ↓ 每次打开重新验证
dsh-market 宿主插件
  ├─ Registry 读取与来源解析
  ├─ 安装、更新、卸载、启停、备份、诊断
  └─ 本地 profile / lockfile / 插件状态
        ↓
dsh-market 客户端页面
  ├─ Discover / Themes / Installed / Advanced
  └─ 搜索、分类、筛选、排序、详情和操作状态
```

市场应用仓库与目录仓库分离。插件作者向 `awesome-dsh-plugin` 目录提交条目，市场应用只消费目录；这使市场 UI 更新和目录运营可以分别演进。

## 3. 当前 dsh-market 已有能力

根据其当前 README，市场已经支持：

- 搜索、分类、下载量、GitHub Stars 和上架新旧排序。
- 双语插件介绍。
- 插件截图与详情预览。
- 评论。
- 独立主题标签页。
- 一键安装、更新、卸载和热启停。
- 插件配置卡。
- 备份恢复与远程同步。
- 插件冲突、重复加载、依赖版本和加载顺序诊断。
- 日志导出和部分自动修复辅助。

它的数据由外部社区目录提供，并通过 JSON Registry 更新；“进入目录”不代表官方或市场作者为插件背书。

## 4. 分类、统计与排序的源码结论

### 4.1 Registry 字段

当前条目核心字段包括：`name`、`owner`、`url`、`npm`、`tarball`、`category`、多语言 `description`、`stars`、`downloads`、`added`、`install`，以及可选的弃用替代和截图信息。

在本次固定快照中：

- 目录声明和实际条目均为 2452 个。
- 22 个类别；条目可以声明一个或多个类别。
- 2173 个条目带 GitHub Stars。
- 1006 个条目带下载量。
- 所有条目带 `added`。
- 没有任何条目带插件级 `updated`。

### 4.2 下载量

`downloads` 的准确含义是“存在 npm 包时，近 30 天 npm 下载量”。没有 npm 包时字段缺失；排序逻辑会把缺失值放在有真实计数的条目之后，再用 Stars 排序，而不是把缺失当成 0。

因此它的下载量存在天然覆盖缺口，也不是 dsh-market 自己记录的安装成功次数。我们的插件可能从 GitHub Release、源码、模型仓库或自有分发服务安装，不能把这一口径直接复制成全市场下载量。

### 4.3 GitHub Stars 与 reaction

Discover 支持按 `stars` 排序，含义是 GitHub 仓库 Stars。市场没有原生 `likes` 字段、点赞写入 API或点赞排序。

评论区通过 giscus 连接统一的 GitHub Discussions，并启用了 reaction；但 reaction 留在讨论线程里，没有汇总为卡片点赞量。用户已经确认本项目不需要另建站内点赞：直接显示 GitHub Stars 的星形数字并支持按 Stars 排序，界面不把它称为站内点赞。

### 4.4 时间

Discover 可按 `added` 升降序，并可筛选最近 1 天、1 周、1 月、1 季度和 1 年加入目录的条目。当前没有插件级更新时间排序。

对本项目而言至少存在三种不同时间：

1. `listedAt`：首次进入市场。
2. `releasePublishedAt`：最新兼容稳定版本发布。
3. `sourceUpdatedAt`：源码仓库最近活动。

三者应分别命名；“最新上架”和“最近更新”也应是两个排序入口。

### 4.5 搜索和分类

搜索按字段加权：插件名与 npm 包名优先，其次作者、描述、类别 ID 和类别多语言名称；用户选定的下载量/Stars/日期作为相同相关度下的次排序。

分类支持数组，当前目录类别是按功能领域组织。我们的插件形态远多于页面，因此建议把“贡献形态”和“创作领域”拆成正交维度，而不是继续扩充一棵混合分类树。

## 5. 安装、更新与本地管理

### 5.1 安装来源优先级

源码明确采用：

```text
仓库身份可验证的 npm 包
  → 作者提供且属于同一 GitHub 仓库的 Release 压缩包
  → GitHub 仓库源码 / monorepo 子目录
```

市场只接受当前 Registry 中的来源，并在安装前确认。这个“目录白名单”与我们的开放方案不同：我们允许未认证插件继续安装，因此需要把“是否收录”“是否认证”“是否允许安装”分开。

### 5.2 更新发现

- npm 安装：读取包源当前版本，使用语义版本比较，只把真正向前的版本作为更新。
- GitHub 安装：读取已安装的固定提交，与远端 HEAD 比较。
- 本地链接安装：尝试匹配目录中的在线来源，提供恢复到在线版本。
- 更新结果缓存 30 分钟；安装、更新或卸载成功后失效。
- 支持单个更新、全部更新、版本说明和来源切换场景。

GitHub HEAD 是移动目标，适合开发型插件，但不一定适合我们正式市场的稳定更新。我们的最终方案需要决定是跟随 Release、manifest 更新通道、固定提交，还是允许插件作者声明多种通道。

### 5.3 已安装管理

Installed 不只显示一张依赖表，还读取版本、实际文件、仓库身份、激活状态、启停状态、插件组、笔记、Bundle、诊断信息和可用更新。它还支持卸载、热启停、更新、全部更新、恢复和加载顺序管理。

可借鉴的重点不是全部 UI，而是把“目录中的插件”和“本机真实安装状态”作为两个数据源进行匹配，不能仅靠插件显示名称猜测身份。

### 5.4 主题插件机制

dsh-market 依赖宿主的 theme service。当前可见主题定义至少包含 `id`、`colorScheme` 和 token 字典；客户端通过 `setTheme(id)` 切换，并监听 `theme/change` 重新渲染。

市场侧还实现了主题插件生命周期：

- Registry 中 `theme` 类别用于识别主题包。
- 已安装主题可以热挂载、热卸载或通过 Loader 启停。
- 激活一个主题时停用其他已安装主题，保持同一组合只启用一个。
- 选择写入本地状态并在重启后恢复。
- 主题有独立市场标签、视觉预览、应用、停用和卸载入口。

这证明“主题插件安装 + 热切换 + 持久化”路径可行。但当前 theme service 的结构主要证明 token 化主题；任意替换顶栏、导航和整个工作区属于更强的 UI/Shell 插件能力，需要另设扩展类型、兼容声明和恢复入口，不能仅根据 `ThemeDef` 推断已经解决。

## 6. 它没有满足本项目的部分

- 没有独立推荐页，也没有专门放置第一方插件的运营货架。
- 没有站内点赞量与点赞排序；本项目接受 GitHub Stars 作为所需的星形热度信号，因此不需要补建点赞服务。
- 下载量仅覆盖 npm 近 30 天，不能跨 GitHub Release、源码和其他分发方式一致比较。
- 时间排序是加入目录时间，没有“最近发布版本”和“源码最近活跃”。
- 分类主要按功能领域，没有把页面、滤镜、Agent、Skill、模型、导入导出等贡献形态独立建模。
- Registry 强制白名单安装，与本项目“未认证插件警告后仍可安装”的开放策略不同。
- 没有把平台认证、第一方所有权和推荐运营位置建成三套独立状态。

## 7. 本项目确认采用的视觉骨架

用户确认市场条目保持简洁，但完整市场不因此删掉分类、推荐、统计和更新：

```text
┌────────────────────────────────────────────────────────────┐
│  推荐  │  插件市场  │  已安装                              │
├────────────────────────────────────────────────────────────┤
│ [图标] 插件名称                      [认证]      [ 下 载 ]  │
│        GitHub 地址                                       │
│        一段简短插件介绍                                   │
├────────────────────────────────────────────────────────────┤
│ [图标] 插件名称                    [未认证]      [ 下 载 ]  │
│        GitHub 地址                                       │
│        一段简短插件介绍                                   │
└────────────────────────────────────────────────────────────┘
```

视觉要求：

- 作者自定义图标位于左侧。
- 名称、GitHub 地址和介绍构成主要信息。
- 下载按钮使用胶囊形。
- 认证状态清晰但不压过插件名称。
- 未认证插件不被隐藏，也不降低排序，只在下载时警告。

## 8. 下载状态

### 认证插件

```text
点击下载 → 正常安装 → 显示已安装
```

### 未认证插件

```text
点击下载
   ↓
显示 GitHub 来源、未审核说明与免责声明
   ↓
取消 / 仍然安装
   ↓
用户确认后正常安装，不削减插件权限
```

## 9. 已安装标签页

完整字段与操作：

- 图标与名称。
- 当前版本。
- GitHub 来源。
- 认证状态。
- 已贡献扩展类型：页面、滤镜、工具等。
- 启用/停用。
- 更新。
- 卸载。
- 可用更新、版本说明、单个更新和全部更新。
- 插件依赖、冲突、加载状态与项目使用情况。
- 更新前恢复点、更新失败回滚和来源变化提示。

## 10. 推荐、排序与指标要求

- 推荐页：平台自有插件、编辑精选、场景集合等运营货架；具体货架待确认。
- 发现页：分类、搜索、兼容性与认证筛选。
- 排序：下载量、GitHub Stars、最新上架、最近更新；可组合升降序的具体交互待设计。
- 指标：市场自己的下载/成功安装数据与 GitHub Stars 等外部信号分开展示。
- 推荐、认证、第一方身份互不替代。

评论、评分、主题专区、备份同步、诊断中心、加载顺序编辑和 AI 修复仍是完整项目评估项，尚未由用户确认是否进入最终产品范围。

## 11. 对本项目的建议分层（尚未定案）

```text
市场客户端
  ├─ 推荐 / 发现 / 详情 / 已安装 / 更新
  └─ 只负责展示与发起操作

在线市场服务
  ├─ Catalog：条目、版本、分类、兼容信息
  ├─ Editorial：推荐货架与第一方展示
  ├─ Metrics：下载/安装统计、GitHub Stars 同步
  ├─ Identity：作者与组织身份
  └─ Certification：认证记录与撤销

本地插件管理器
  ├─ 解析来源、下载、安装、启停、更新、回滚
  ├─ 发现 UI/时间轴/滤镜等贡献和冲突
  └─ 向市场回报匿名或账号关联的安装结果（需用户同意与口径设计）
```

这三层分开后，在线市场不能直接修改工程；本地插件管理器也不需要承担推荐和 Stars 同步业务。

## 12. 尚待决定

- 插件作者如何提交 GitHub 仓库。
- 市场目录由谁托管和维护。
- 插件 manifest 的必填字段。
- 图标尺寸、格式和缺省图标。
- 下载的是 Release 包、源码还是平台构建产物；是否允许同一插件声明多种来源。
- 插件更新跟随 Release、包管理器版本、固定提交还是可选通道。
- 认证徽章的申请、版本继承和撤销规则。
- GitHub Stars 的同步频率、API 配额处理和最后刷新时间展示。
- 下载量采用下载点击、成功安装、独立设备还是外部包源数据。
- 推荐页具体货架、排序规则和第一方插件占位规则。
- “更新”放在已安装内部还是独立顶级标签页。
